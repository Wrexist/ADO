# Profile backup and recovery review

Restoration writes to `.restore-in-progress.sqlite`, verifies the copied bytes against the manifest, and records a fresh restore identity in the SQLite `controlos_restore_guard` table before exposing `acc.sqlite`. The version 2 marker binds that identity, the source-backup checksum and restoration time. Startup inspects the actual configured database (including custom filenames) before migrations, scanners, automation or queue recovery. A missing, exchanged or downgraded marker, missing/invalid database guard, or remaining staging file stops startup. Restore-of-a-restored-backup receives a new identity and returns to review mode. The marker is finalized with the existing flushed, guarded atomic file replacement.

A valid, still-present version 1 marker is enrolled on first startup: the guard is committed before its marker is upgraded. Interruption between these writes fails closed and requires recovery into a new directory. This cannot retroactively identify a legacy restored profile whose only marker was already deleted before enrollment. The binding is an accidental-loss/mismatch guard within the same-OS-user trust boundary, not tamper-proof storage against a user who can rewrite both the database and marker. The stored database checksum identifies the source backup; normal subsequent profile changes do not have to retain that entire-file checksum.

`restoreGuard.test.ts` covers marker loss/exchange/downgrade, a custom configured database filename, a fresh binding when restoring a previously restored backup, legacy enrollment and incomplete staging. `copyIntegrity.test.ts` injects corruption into the actual copied file and checks source preservation and refusal to expose `acc.sqlite`.

The current packaged Windows probe additionally withholds the marker after two normal restored-profile starts and requires startup refusal, exit code 1 and a byte-identical database. The first native probe exposed Electron returning 0 despite `process.exitCode = 1`; desktop now sets the failure status at `will-quit`, after the existing `before-quit` cleanup. Three normal legacy migration/reopen launches also passed with the same artifact. [Source, probe and artifact hashes](restore-binding-evidence.json) bind this evidence to the current implementation; the historical packaged evidence below remains a prior checkpoint. This is still an unsigned unpacked app with synthetic profiles, not installation, update/rollback or a real user-profile drill.

Profile backups use SQLite `VACUUM INTO`. Version 2 manifests include SHA-256 checksums for the database and each included configuration file. A repeated backup stamp is rejected without replacing the existing snapshot. Restore accepts legacy version 1 manifests, checks database integrity and foreign keys, and requires a new destination directory.

`connections.json` and the desktop access key are omitted from new manifests. Legacy connection files are also omitted during restore. This is not general secret redaction: historical prompts, events and other user-authored data can contain sensitive information. Protect backup storage accordingly. Local repository contents, uncommitted work, result repositories and installed tools are not included.

Run `npm run restore -- <backup.sqlite> <new-profile-directory>`. A persistent `restore-state.json` puts the new profile in recovery review mode. Interrupted or invalid markers fail startup instead of enabling execution. Start the CLI server with `DB_PATH` pointing to the restored `acc.sqlite`, or desktop with `--profile-dir=<absolute-directory>`.

In review mode, history remains readable, browser pairing works, queued jobs do not resume, old locks are not reconciled or released, scanners and system automation do not start, and mutating API requests return HTTP 423 except the explicit recovery-review/activation flow. Desktop skips its update check. The interface displays the recovery warning. This is not a byte-for-byte read-only database: opening a profile can apply schema migrations and initialize metadata.

There is no automatic promotion to an active profile. Do not remove the marker to bypass review. **Resume manual operation** performs a fresh check, then requires the exact typed confirmation `ENABLE MANUAL OPERATION`. The five-minute, one-use review token binds the inspected run/verification/lock records, local references, result comparisons and profile JSON hashes. Confirmation repeats the inspection and refuses stale state. The marker is replaced using the existing identity/content preservation guard, a flushed temporary file and rename. The current session remains paused; restart with the same profile to enter manual operation.

Activation refuses unresolved queued/running jobs, running verifications, retained locks, recorded uncertain process termination, nonmatching/unknown local identities, and completed workspaces without matching content evidence. Activation itself cannot cancel jobs, discard results or release locks. The separate unstarted-queue review below can resolve eligible waiting jobs. Process/lock resolution and reference rebinding still need additional supported workflows. Legacy history without a workspace remains historical and is not promoted to verified evidence. Foreign-key checks do not prove that referenced files, repositories or remote resources still exist.

**Review restored queued jobs** offers explicit cancellation only for versioned queue records without recorded process identity/termination, workspace/result, execution counters, verification attempts or a lock owned by that run. Bound tasks must still have the exact queued lifecycle revision. Review exposes a digest of the current run, binding, task and related ownership records. The user types `CANCEL QUEUED JOB`; the authenticated recovery-only endpoint rechecks everything inside the SQLite transaction. Running, legacy, ambiguous and stale records are refused. Cancellation is also refused during another recovery review or after activation has been approved pending restart.

Cancellation retains the run as failed with an explicit recovery cancellation note, transitions a linked task to blocked using the existing versioned lifecycle, and records both build-state and audit events atomically. A failed audit write rolls back the run/task/history changes. No process is killed and no lock is released, including another writer's lock on the same repository. No verification or acceptance is fabricated. The profile remains in review until a separate activation passes.

Ordinary clean shutdown now preserves versioned queued intent, just as crash recovery does. Closing the host is not a request to cancel waiting work. After normal startup, the existing scheduler can resume such jobs once; a recovered manual profile additionally waits for a completed explicit project scan. Legacy queued rows retain their previous conservative shutdown handling. Active-process stop/quarantine behavior is unchanged. `runner/recovery.test.ts` covers clean SQLite close/reopen, exactly-once execution and idempotent redispatch. `backup/queue.test.ts` covers stale/ambiguous refusal, task history, retained unrelated locks, audit-failure rollback and replayed queue state. The API restore test exercises authenticated cancellation and preservation of the other running record/lock.

Manual recovered profiles keep startup scanners, scheduled/event automation, automatic model-based incident diagnosis and desktop update checks off. Environment-provided provider credentials remain ignored. Add/re-enter credentials and explicitly add/rescan project folders before execution. New persisted queued jobs wait for that explicit scan after later restarts rather than failing because no scanner is loaded. Planning/configuration mutations are available after activation. Explicitly requested integrations and jobs retain their usual policy/approval checks; this mode does not provide an OS sandbox or alter the same-user trust boundary.

`activation.test.ts` checks unauthenticated/forged confirmation refusal, stale configuration, retained queued-job/lock blockers, exact confirmation, the paused pre-restart session, normal planning writes after restart, disabled startup services, deferred new queued jobs and invalid manual markers. Its removal of synthetic blocking rows creates a separate idle fixture; no production activation endpoint removes those rows. Browser smoke separately exercises blocked and idle-profile confirmation fixtures.

The recovery banner offers **Inspect restored references**. The authenticated report inspects registered checkouts, recorded run workspaces and verification workspace paths on demand. It distinguishes matching physical identities, missing directories/Git metadata, replaced identities, checkouts registered on another host, insufficient identity records and unreadable/invalid metadata. Checkouts on another host are not inspected. It invokes no Git commands or agents and changes no stored references or locks. Counts describe restored queued/running records and retained locks; they do not establish that any process is currently alive.

An identity match checks the recorded local directory/Git identity only. It does not verify HEAD, file contents, uncommitted work, remote availability, sandboxing or termination. The observation is dated and may become stale immediately after the check. Running the report never enables execution. Missing local work must be recovered separately from the metadata backup; unpushed code can be lost even when the metadata snapshot is intact.

For a recorded run workspace, **Compare saved result** separately compares the observed HEAD and content fingerprint with that run's saved result. It reports matching, differing, unavailable, or insufficient saved evidence. The comparison is serialized per server and requires an authenticated request to a restored profile. It does not run the project's verifier, create new verification evidence, change an old judgment, release locks or activate the profile.

The comparison uses temporary private Git metadata: copied index, observed HEAD, a local object-store reference and an allowlist of non-executable core settings. It does not import repository filter commands, fsmonitor configuration, hooks, remotes or global configuration into that view. Git external diff/textconv and network protocols are disabled; submodules are refused for separate review. Metadata queries against the original repository only use `rev-parse` and `config`. The temporary view is removed afterwards. This avoids invoking project-defined transformations during the comparison; Git documents such transformations in [gitattributes](https://git-scm.com/docs/gitattributes) and [fsmonitor configuration](https://git-scm.com/docs/git-config#Documentation/git-config.txt-corefsmonitor).

This remains a bounded observation using the existing fingerprint algorithm, not an atomic filesystem snapshot or universal backup of code. Ignored files are outside the recorded result contract. Local/global attribute and exclusion configuration is not imported; repositories depending on it or filters may report a differing fingerprint and need manual review. Missing objects/Git tooling, oversized untracked files, submodules and changed physical identity return unavailable. Matching cannot prove process termination or safe activation, and concurrent filesystem changes remain possible inside the same OS-user trust boundary.

`content.test.ts` compares a real temporary repository, checks binary and leading-space untracked changes, seeds filter/fsmonitor/external-diff execution canaries, and verifies unchanged index/config/run rows. The restore API test checks authentication and legacy missing-evidence behavior. Browser smoke exercises the explicit content-comparison fixture at desktop/mobile sizes.

Validation: `backup.test.ts` covers credential omission, checksum tampering and preservation of duplicate-stamp backups. `recovery.test.ts` restores an actual temporary SQLite profile and starts the server twice with system services requested, checking zero process starts, unchanged queued/running rows and locks, denied mutations, readable history and interrupted-marker refusal. Browser smoke uses an explicit display fixture at 1536 and 390 pixels. These checks do not establish full T36 acceptance, a real user-profile restore, installer recovery or a complete crash matrix.

`references.test.ts` uses an actual temporary Git repository with dirty and untracked work. It checks missing, replaced, foreign-host and legacy identities while preserving files, index, config and database rows. The API restore test additionally checks authentication and retained pending-run/lock counts.

For the packaged Windows path, run `node --import tsx scripts/probe-packaged-restore.mts <unpacked-executable>`. Build using the isolated dependency workspace described in [packaged-profile.md](packaged-profile.md). The probe creates its own source profile, local Git working copy, project/repository/checkout, task, queued/running records, retained lock and credential canaries. It makes a real backup, restores to a new directory and launches the real packaged desktop twice. It checks the renderer/preload API, reference panel, absent restored provider credentials, denied mutation, unchanged restored rows, SQLite integrity/foreign keys and preserved dirty work/Git index after normal shutdown. Temporary profiles are retained separately. See [artifact evidence](packaged-restore-evidence.json).
