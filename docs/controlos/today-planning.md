# Today proposal foundation

`POST /api/planning/today` is an authenticated, read-only preview over a single database snapshot. It accepts `availableMinutes` (1–1440), nullable `projectId` and `lockedTaskId`, and user estimates containing `taskId`, `taskVersion`, `minMinutes` and `maxMinutes`. Estimates are supplied for this request, not invented or silently persisted. Duplicate estimates, inverted ranges and stale/missing task versions are rejected.

The response contains at most three alternatives, not an agenda to execute together. Each alternative's upper estimate must fit the entire window and is explicitly labelled “User estimate; actual duration is unknown”. Manual task priority orders alternatives, followed by creation time and stable identity. A locked focus excludes every other task, even one with higher priority; a blocked or over-budget focus produces no substitute.

Project focus, active project lifecycle, ready task status, recorded dependencies and retained writer locks are eligibility filters. Locks also exclude new tasks in the same registered repository, even without a task-to-run binding. Recorded execution checkout, scanner source, Git identity, canonical checkout path, canonical GitHub resource and verification-attempt repository metadata resolve ownership. A missing run, unresolved repository or missing/mismatched verification attempt produces `writer_scope_unknown` for repository-bound tasks; manual tasks without a repository remain eligible unless their own attempt holds a lock. This is a conservative metadata preview, not fresh filesystem identity or execution preflight. Unknown estimates are excluded instead of treated as zero. Exclusion reasons are returned, along with task versions, generation time and the applicable window. The endpoint writes no task, revision, run or calendar and invokes no provider.

The lock API regression uses synthetic registered repositories and historical run/verification rows. It checks exclusion across tasks, preserved independent-repository alternatives, scanner/Git/path/GitHub ownership, exact repository names, unknown scope, missing and mismatched verification attempts, unchanged lock/planning state and restored alternatives after fixture lock removal. It does not terminate a process, release a production quarantine lock or certify physical sandboxing. Reproduce with the same `todayApi.test.ts` command below.

The API regression creates a synthetic on-disk profile through production project/task endpoints. It checks authentication, a 30-minute window, locked focus, missing/over-budget estimates, blocked dependencies, manual priority, the three-choice cap, stale estimate rejection and unchanged plan/history/run state. Reproduce: `npx vitest run apps/server/src/projects/todayApi.test.ts`. Local log: `controlos-today-focused.log`.

The `/today` page is available from desktop/mobile navigation and Tasks & Inbox. It lets the user set a time window, project/task focus and estimate ranges, then explains alternatives and exclusions. Loaded/generated timestamps and task versions are visible. Editing inputs clears the previous proposal; refreshing planning retains draft estimates with their old task version and warns when the task changed. The server rejects stale estimates. A failed request clears the old proposal and shows the error. Controls are keyboard accessible and proposals announce their result count.

The built-browser probe `node --import tsx scripts/probe-today.mts` uses a synthetic profile with the production API. It checks a 30-minute locked focus, uncertain estimates, priority preservation, over-budget and dependency exclusions, stale version rejection, explicit estimate refresh, keyboard submission and network failure at 1536/390 px. It compares planning snapshots around proposals and verifies zero runs. Screenshots are explicitly DEMO data. [Source, build and screenshot bindings](today-ui-evidence.json) document the tested artifact.

T08 is locally passed for this manual planning scenario and revalidated with saved profile choices. Both final screenshots were visually reviewed. The initial UI logs are `controlos-today-ui-probe-final.log`, `controlos-today-ui-verify.log`, `controlos-today-ui-final-typecheck.log` and `controlos-today-ui-final-lint.log`; the preference extension is evidenced below. This does not certify the complete REQ06 or R2 gate.

Today choices can now be explicitly saved in the current profile. `GET/PUT /api/planning/today/preferences` stores one validated choice set with a monotonically increasing version and save timestamp in SQLite (migration 0020). Reads of an empty profile return unsaved defaults without inserting a row. PUT requires the version last read and current task-version estimates. A conflicting writer receives 409; no later state is overwritten. Invalid stored JSON blocks reading/saving instead of silently resetting it. A failed transaction leaves the previous choice set intact.

The page loads saved choices on entry. “Refresh planning” preserves unsaved page edits and their estimate versions; “Load saved choices” explicitly replaces page edits and adopts the current saved version. If a task changed but its duration estimate remains appropriate, “Use estimate for current task” explicitly confirms that version binding without forcing a different number. Save success is only shown after the server confirms it. If a save is unconfirmed, the page retains its draft and asks the user to load saved choices before retrying. No proposal is automatically generated or job started by loading or saving preferences.

Estimates outside the currently rendered task list appear in “Other retained estimates”, including archived or unavailable tasks. A stale hidden estimate can otherwise prevent every save while giving the user no editable field. The panel identifies these estimates and offers explicit removal from the draft. The stored choices remain unchanged until Save choices succeeds; focus and other estimates are retained. The browser probe archives a task after its estimate was saved, verifies save rejection, removes only that estimate and checks the exact stored remainder at both viewport sizes. Reviewed screenshots: `smoke-shots/today-retained-1536.png` and `smoke-shots/today-retained-390.png`. Log: `controlos-today-retained-probe.log`.

The preference API regression checks restart, separate profiles, conflicting writers, stale task estimates, injected commit failure and corrupt stored JSON without reset. The built-browser probe also checks explicit save, reload and concurrent-write recovery at both viewport sizes. Its first run exposed the missing unchanged-estimate confirmation; the final run passes with the explicit button, retaining strict server version checks. Logs: `controlos-today-preferences-focused.log`, `controlos-today-preferences-verify.log`, `controlos-today-preferences-probe.log` (initial failure) and `controlos-today-preferences-probe-final.log` (pass). The database is included in ordinary profile backups, but native packaged upgrade and restore acceptance for this new migration have not been rerun.

Review of execution policy/environment remains to be implemented. Dependencies here are the recorded planning snapshot, not a fresh filesystem re-verification of accepted work. The response explicitly requires separate execution eligibility review; it does not promise a task can safely be dispatched. No calendar integration or automatic mutation is introduced. REQ06 and the full R2 gate remain open.
